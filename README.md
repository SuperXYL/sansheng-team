# 使用介绍 · 三省六部智能体团队（sansheng-team）

> 给第一次使用的人。架构与设计动机见 [README](../README.md)，协议全文见 [PROTOCOL.md](../PROTOCOL.md)，本文只讲**怎么用**。

## 这是什么

一个按唐朝**三省六部制**运转的多智能体协作团队：决策（中书出令）、审核（门下封驳）、执行（尚书派工六部）三权分立，外加核验、记忆归档、人工闸门。你扮演的角色很简单——**下旨**，团队按制把差事办完、把复旨交回来。

适用：研究报告、数据分析、工程实现、合规质检、长任务多步编排。不适用场景见文末[边界](#什么时候不要用它)。

## 一分钟上手

| 平台 | 安装 | 开始使用 |
|------|------|----------|
| **WorkBuddy** | 导入 `adapters/workbuddy/`（专家包），或直接装打包好的 zip | 启用专家团后开口下旨即可，主理人自动编排 |
| **Codex CLI** | 把 `adapters/codex/AGENTS.md` 放到仓库根目录 | 对 Codex 说"按 AGENTS.md 三省六部流程办这道旨意：…" |
| **DeepSeek Harness** | `cp -r adapters/deepseek-harness ~/.dsh/plugins/sansheng-team && dsh plugin load ~/.dsh/plugins/sansheng-team/dsh-plugin.json` | 同上，按 dsh 多智能体接线调度 |

其他平台：把 `adapters/` 里的 9 个角色提示词当系统提示词加载，照 `PROTOCOL.md` 流程编排即可——**协议是产品本体，运行时只是宿主**。

## 怎么下旨

三个约定，掌握后就能用：

1. **说清交付物和验收标准**——"出一份带数据来源的报告"比"分析一下"高效一倍
2. **可以像点将一样点名**——"着户部查数据、礼部成文"；不点名则由尚书省自动归口
3. **原文会被透传**——你的旨意原文（`user_raw`）全程强制透传到每个执行体，不怕中转走样

示例旨意（可直接照抄改）：

```text
朕下一道旨意：调研近一个月 AI Agent 热门用法，对比 A 与 B 的用法差异，
以 GitHub 数据源为依据出一份报告。要求结论先行、优缺点对照加雷达图、
数据带采集时点、事实论断标注可信度。
```

## 一次任务的完整生命周期（实例回放）

以下是一道真实旨意的办理过程，让你知道每一步幕后发生了什么：

| 环节 | 谁在干活 | 干了什么 |
|------|----------|----------|
| ① 分流 | 主理人 | 判定为 L2（复杂交付物）→ 进全流程 |
| ② 草拟 | 中书省 | 把旨意转成精确提示词，形成《诏书》：目标/约束/拆分建议/验收标准 |
| ③ 审核 | 门下省 | 七维校验 → **画押**（附非阻断建议："数据带采集时点"） |
| ④ 派工 | 尚书省 | 拆 3 个并行子任务 + 指定触发 Skill，签发任务契约 |
| ⑤ 执行 | 户部+礼部+工部（并行） | 户部采 GitHub 数据、礼部成文、工部出图表 |
| ⑥ 汇总 | 尚书省 | 汇编《执行汇编》，列超时/缺件 |
| ⑦ 核验 | 刑部 ∥ 门下（并行） | 刑部逐条核事实标可信度；门下对照验收标准终检 |
| ⑧ 复旨 | 主理人 | 按「结论 → 依据 → 风险」交付；吏部同步记忆归档 |

结果：报告一份，其中 6 条事实论断被标注为 2 条已证实、2 条基本可信、2 条存疑——**存疑的会被明示，不装作确定**。

## 你可以这样指挥团队

| 用法 | 说法示例 | 效果 |
|------|----------|------|
| 全流程办差 | "朕下一道旨意：…" | 走完分流→草拟→审核→派工→执行→核验→复旨 |
| 点名单部 | "着户部统计这组数据" | 轻量直调，跳过全链路 |
| 多部并行 | "着户部查数据、工部写代码、礼部排版" | 同波并行，各产出后汇总 |
| 幻觉核查 | "着刑部核查以下结论是否掺杂 AI 幻觉：…" | 逐条查证据，标已证实/基本可信/存疑/已证伪 |
| 交付质检 | "着门下省对照验收标准终检这份交付物" | 准予呈御 / 发还补正 |
| 记忆归档 | "着吏部起居注：把本轮偏好归档" | 形成结构化记忆条目 |
| 封驳重审 | "驳回，理由：验收标准不完整" | 退回中书重拟（最多 2 次，之后升级人工决策） |

## 哪些任务走全流程（L0-L3 分流）

不必担心"一句话也要过九堂会审"——协议内置风险分级路由：

| 级别 | 任务类型 | 流程 | 体感 |
|------|----------|------|------|
| L0 | 闲聊、单一事实快问 | 直接应答 | 秒回 |
| L1 | 单步小任务 | 规划 → 1-2 个执行体 → 确定性检查 | 快 |
| L2 | 多步/交付物/复杂分析 | 全流程 | 中 |
| L3 | 外发/发布/删除/生产写入 | L2 + 最小权限 + 演练 + **人工批准** | 慢而稳 |

## 输出长什么样

复旨固定结构，方便你直接验收：

```text
结论：…（先行）
依据：…（逐条，事实论断带可信度标注）
风险：…（含死信任务、预算使用、存疑项）
```

## FAQ

**封驳会不会无限打回？** 不会。封驳最多 2 次，之后强制升级为人工决策点，由你裁决。

**每次都全员出动，费钱吗？** 不会。六部是能力标签，实际每道旨意只启动 1-4 个执行体（动态执行池）；预算 80% 预警、100% 熔断。

**危险操作会乱来吗？** 不会。外发、发布、删除、生产写入一律走人工批准闸门；PLC 下载与现场控制**永远默认禁止**。

**部门之间会不会互相串话失真？** 所有信息流经主理人中转，且任务契约强制透传你的旨意原文；冲突按「安全 > 合规 > 事实 > 格式」固定序仲裁。

**换平台要重写吗？** 不用。9 个角色提示词与协议是运行时无关的 Markdown，换宿主只需换入口。

## 什么时候不要用它

- **单点快问快答**：普通对话直答更快（团队会自动 L0 分流，但你自己知道更好）
- **硬件在环/现场设备控制**：协议层面永不授权（PLC 下载等）
- **在线高并发低延迟服务**：这是协作编排框架，不是在线 serving 架构
